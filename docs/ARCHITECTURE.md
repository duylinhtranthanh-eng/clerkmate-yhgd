# ClerkMate — architecture

*This is the detailed technical document. For the short overview, start with the
[README](../README.md).*

**“Từ ghi chú nhanh đến bệnh án hoàn chỉnh.”**
*From bedside notes to structured clinical learning records.*

A mobile-first, local-first clinical **learning record** for Family Medicine students and
postgraduate trainees. Not an EMR — a scaffold for learning how to think about a patient.

```
LEARNER PROFILE → QUICK CAPTURE → STRUCTURED RECORD → COMPLETENESS CHECK
→ GENOGRAM → REFLECTION → REVIEW → EXPORT
```

## Run it

```bash
npm install
npm run dev
```

Then open the printed URL (default `http://localhost:5173`). On a phone, use the network URL
that Vite prints — the dev server binds all interfaces.

```bash
npm run build && npm run preview        # production bundle, with the service worker
npx tsc -p tsconfig.app.json --noEmit   # typecheck
node scripts/make-icons.mjs             # regenerate the PWA icons
```

No accounts, no server, no API keys. Everything lives in the browser's IndexedDB.

## Deployed

**https://clerkmate-yhgd.netlify.app**

```bash
npm run deploy                    # build + push to Netlify
node scripts/make-share-qr.mjs    # printable QR for the live URL → share/
```

Two things about the live site worth knowing:

- Netlify enables *require Netlify login* on new free-tier sites, which returns 401 to everyone.
  It is off for this site (`sso_login: false`).
- The CSP in `netlify.toml` sets `connect-src 'self'`, so the browser **enforces** that the app
  reaches nothing external. Verified live: `fetch('https://example.com')` from the page is blocked.
  That turns the privacy claim from a promise in this README into something a judge can check in
  DevTools.

## Deploying elsewhere

`npm run build` produces a handful of static files — one HTML, one JS, one CSS, a service worker,
a manifest and four icons. Drop `dist/` on any static host (Netlify, Vercel, GitHub Pages, the
university's own web server). There is nothing running server-side, so hosting costs nothing and
the server never sees a record.

### It installs and works offline

ClerkMate is a PWA. On a phone, *Add to Home Screen* gives it its own icon and name and opens it
full-screen without browser chrome; on Android the maskable icon adapts to the launcher shape.

The service worker (generated by a ~60-line plugin in `vite.config.ts`, not Workbox — the
precache list is nine files and deserves to be readable) precaches the shell and serves
navigations from cache. That matters here more than for most apps: a student is standing in a
commune health station with no signal. The records were always safe in IndexedDB, but before this
a reload with no connection produced a blank page.

Verified by killing the preview server and reloading: the app opens, a new profile and case can
be created offline, and both survive another reload. Updates never swap the app out mid-note —
a new build waits, and a small bar offers *Tải lại* when the learner is ready.

## Privacy posture

- Local-first: `IndexedDB` only (`clerkmate` database, stores `cases`, `blobs`, `meta`).
- No authentication, no cloud sync, no external requests at runtime — zero runtime
  dependencies beyond React.
- The first-run **learner profile** (name, student ID, year, class) is an identity label for
  the record, not authentication: no password, nothing verified, nothing sent anywhere. It is
  printed on the exported record so a teacher knows whose work it is.
- Insurance is recorded as yes/no only — the app never asks for a card number.
- Backup / restore writes and reads a single local JSON file (Settings screen). Nothing is
  uploaded.
- Clearing browser data or using private browsing loses the cases — back up before a demo.

The storage seam is deliberately narrow: `src/db/idb.ts` plus `src/db/repository.ts` are the
only modules that know about persistence, so a later encrypted or server-backed store means
reimplementing those two files and nothing else.

## Architecture

```
src/
  types/case.ts            Central CaseRecord model — UI-agnostic, no React, no DOM
  types/profile.ts         Learner profile (name, student id, level) — a label, not a login
  types/factory.ts         createEmptyCase() + migrateCase() schema-migration hook
  config/                  All educational content as data, never inside components
    sections.ts            Section catalogue (labels, groups, blurbs)
    requirements.ts        Requirement catalogue: id → predicate over CaseRecord
    levels.ts              Y2 / Y5 / Y6 / SDH tier assignment + inheritance
    clinical.ts            Starter reference lists (exam systems, codes, red flags…)
    risk.ts                Risk domains + factors, ordered as a teaching sequence
    demoCases/             Fully worked fictional cases, registered in index.ts
  completeness/engine.ts   Pure evaluateCompleteness(record, level) → snapshot
  parsing/                 Quick-note → structured suggestions
    types.ts               NoteStructurer interface + StructuringSuggestion (plain data)
    heuristicStructurer.ts Deterministic offline Vietnamese/English parser
    apply.ts               The only code that turns a suggestion into record data
  genogram/                layout.ts (geometry) + patterns.ts (condition key)
                           + lifeCycle.ts (Duvall suggestion) + GenogramSvg.tsx
  workflow/                status.ts (the 8 processing states) + submission.ts (the hand-in flow)
  db/                      idb.ts (IndexedDB wrapper) + repository.ts (the only storage API)
  export/                  CaseDocument.tsx (print-ready) + exportPdf.ts
  screens/                 One screen per step, sections/ for the record editors
  components/              UI primitives, no clinical knowledge
  styles/                  index.css (design system) + print.css (the PDF)
```

### Data model

One `CaseRecord` per case, versioned by `schemaVersion`. `migrateCase()` merges a stored
record onto a fresh blank one, so records written by an older build keep opening and new
fields simply arrive empty. The model never imports from the UI.

### Risk review as a teaching sequence

`config/risk.ts` holds nine ordered domains, and the order is the lesson:

1. **Nguy cơ cấp cứu** — what could harm this patient today, reviewed before anything else
2. Hành vi — lối sống · 3. Tim mạch — chuyển hóa
4. **Ung thư** — self-filtered by age and sex (`appliesWhen`), so a 25-year-old is never asked
   about prostate screening and a male patient never sees cervical screening
5. Lão khoa · 6. Nhận thức — gated on age
7. Tâm lý · 8. Xã hội — the Family Medicine layer
9. Môi trường — nghề nghiệp

Each factor carries a one-line `why`, so the checklist teaches while it is used. The screen
opens one domain at a time with a per-domain "Tất cả không" so a learner can clear a domain in
one tap and then flip only what applies — a bulk "no" never overwrites a positive finding.
Positive emergency findings raise a banner telling the learner to act before finishing the
chronic-care plan.

**Gating is clinical, not just chronological.** `riskContext(record)` derives hints from what
has already been documented, so falls, home hazards and frailty apply to a 58-year-old with
knee osteoarthritis and quadriceps wasting, not only to someone over 60; lung-cancer risk shows
only for a patient with a smoking history. When age or sex is still blank nothing is hidden, and
a factor the learner already answered is never hidden by a later demographic change.

**The social domain does not ask again.** SCREEM and Family APGAR already cover support
networks, economics, health literacy and access to care, so domain 8 reads those back and links
to the Family Medicine assessment to edit them. The only question left there is the one SCREEM
has no place for — domestic violence, which has to be asked privately.

#### Investigations: ordered fast, read carefully

The two halves of this section are used at completely different moments, so they ask for
completely different amounts of writing.

**Ordering happens on the buổi khám.** It is a tap-to-add list of test names and nothing else.
There used to be a `rationale` field per test; it came out after the first round of feedback —
demanding a written justification per test turned a ten-second job into a writing exercise, and a
learner standing at the bedside skips the whole section rather than do it. The reasoning has not
been dropped, it has been moved to where there is something to reason from.

**Reading happens later, and is where the effort belongs.** Every result carries the date the
specimen was taken (not the date it was typed), a bình thường / ranh giới / bất thường flag, and
its own interpretation line. A result can be **typed or photographed** — a photo of a lab slip
*is* the result, so it sits on the result row with the same date and the same required
interpretation rather than in a disconnected attachment list, and it can be redacted without
leaving the screen.

Above that sits the synthesis block, which asks four questions instead of offering one blank box:
which results are abnormal and in which direction, what they support or argue against, which do
not fit the clinical picture, and what changes in the plan because of them. The last is the
pointed one — a test that changes nothing was probably not indicated. Abnormal results are named
in a banner so they cannot be quietly skipped.

### Attachments carry patient identifiers

A photographed lab slip, ECG or old prescription almost always has the patient's name, ID and
date of birth printed across the top — which would defeat every other privacy measure in the app.

So `components/RedactEditor.tsx` paints them out: drag boxes over the image (or tap *Che dải trên*
for the usual identifier band), and on apply the boxes are drawn onto the **full-resolution**
bitmap, the image is re-encoded, and the result **overwrites the stored blob**. The redaction is
destructive by design — an overlay, a CSS mask or a separately stored crop would all leave the
name sitting in the file for the next export to find. Verified by pixel inspection: the redacted
band goes from 3,648 dark text pixels to 43,200/43,200 pure black.

Any case can pull in a mock lab slip — **Chèn ảnh xét nghiệm mẫu** in the attachments section —
because the people most likely to be trying the redaction tool are exactly the people with no lab
photo to hand.

**A flag is not a fact, so the export gate is a file, not a boolean.** Ticking "no identifiers here"
used to be enough to let the picked file itself be exported — with whatever EXIF, GPS coordinates
and camera serial the phone wrote into it. Now every attachment has to produce a *derivative* before
anything can leave the device, and `sanitizedBlobKey` holds it:

```
raw local blob  →  redact  or  declare-no-identifiers  →  sanitized derivative  →  PDF / export
```

Both paths re-encode through a canvas at natural resolution, so metadata has nowhere to survive;
the redaction path additionally overwrites the original. The picked file stays on the device as the
working copy and is never the thing exported. `workflow/privacy.ts` is the single place that decides
what may travel, and it **fails closed** — a record too old to have the field, or malformed for any
other reason, exports nothing. An attachment with no derivative is dropped from the printed
thumbnails and its list entry says the image was withheld.

Clinical photos (`clinical_photo`) carry one extra question, asked before the camera opens and again
in the viewer: is a face visible? A declared face **blocks the image** — it cannot be redacted or
declared clean, and it is withdrawn from every export path. Blurring eyes is not offered, because a
blurred face is still a photograph of a person that was taken and stored; the app asks for a crop or
a retake instead. An unanswered face question also blocks, so silence is not a way through.

Every attachment still tracks `redacted` and `privacyChecked` for display; unchecked images are
badged *chưa che* on the thumbnail, warned about on the review screen before export, and labelled in
the exported list. At Y5 and above, having checked them is a mandatory completeness item — measured
now against the derivative, not the flag. Deleting a case or an image deletes both blobs, and a
backup carries both.

### Recall before recognition

A complete checklist has a cost: it trains *recognition*, which is far easier than *recall*, and
recognising a risk when you see it listed is not the skill a clinician needs. So the checklist is
gated. For each domain the learner first writes what they can think of for this particular
patient, then reveals the list; their own notes stay pinned above it and the items they had
mentioned are badged, which turns the checklist into a self-test rather than an answer key.

`risk/recall.ts` reports **matches only**. It never tells a learner they "missed" something,
because a keyword heuristic is not good enough to make that claim — they may have meant it in
other words. Keys can be multi-word (all words must appear somewhere), and generic words are
excluded so "giảm thị lực" does not get credited as "suy yếu — giảm hoạt động chức năng".

#### Scaffolding fades with level

How much help a domain gives depends on the learner's level (`RISK_MODE_BY_LEVEL` in
`config/risk.ts`), because a Y2 student has no schema to recall from while an SDH learner who
only recognises risks off a list has not learnt what the app was built to teach.

| Mode | Level | What the learner sees |
|------|-------|-----------------------|
| `checklist` | Y2 | The full item list, ticked off |
| `recallThenChecklist` | Y5 | Write from memory, then the list appears with matches badged |
| `generate` | Y6, SDH | **No item list.** Only the domain's structural prompts ("chỉ số chuyển hóa đo được", "tiền căn gia đình", "tổn thương cơ quan đích") — the shape of the thinking, not the answers |

Two deliberate exceptions to the fade:

- **Nhóm 1 — Nguy cơ cấp cứu keeps its full checklist at every level** (`alwaysChecklist`).
  Checklists are the right tool for do-not-forget items and the wrong tool for generative
  reasoning, which is why surgical and aviation checklists are given to experts rather than
  withdrawn from them. A senior learner forgetting to ask about suicidal ideation or
  hypoglycaemia is a miss, not a teachable moment.
- **Nhóm 8 — Xã hội** is read from SCREEM at every level, since asking again would duplicate it.

In `generate` mode there is **no skip button**: a free tap past the exercise is how the exercise
stops happening. The only ways forward are to commit a list, or to state that the domain was
reviewed and nothing found — a clinical statement, not an escape hatch, and one that records
"không" against that domain's factors. The catalogue then appears explicitly framed as an
**after-action review**: what you named is badged, and what you did not is there to ask yourself
why. Turning `recallFirst` off in Cài đặt drops every domain back to plain checklists.

Alongside it, every domain has **"Yếu tố khác bạn nghĩ ra"**: the catalogue can
never be complete, so learner-added factors go into the record like any other, are never filtered
out by age or sex, and print marked as `[người học tự nêu]`. The learner's pre-checklist notes
also print in the exported record, so a teacher can see what the student generated unaided —
which is more diagnostic of their thinking than the finished chart.

That feedback loop already paid for itself: a test recall listing "hạ đường huyết" matched
nothing, which is how hypoglycaemia and head trauma came to be added to the emergency domain.

#### Graded assessments

Beyond present/absent, three domains carry a graded assessment. All are optional: a learner
opens one when the case calls for it.

- **Falls** — the CDC STEADI three-question screen plus Timed Up and Go and the 30-second chair
  stand. The band (thấp / trung bình / cao) comes from a rule printed on the screen next to the
  result (`config/falls.ts`), so nothing is scored invisibly, and each band lists the
  interventions worth considering.
- **Depression and anxiety** — PHQ-2 → PHQ-9 and GAD-2 → GAD-7 (`config/scales.ts`). The
  follow-up scale stays hidden until the screen is positive, then the app offers it. PHQ-9
  item 9 raises a safety banner and a one-tap action to flag the emergency risk.
- **Insomnia** — ISI, recorded as a total with its severity bands.
- **Cognition** — Mini-Cog: three-word recall plus clock drawing, 0–5, positive at ≤2.

**Licensing decides which instrument ships with items.** PHQ, GAD and Mini-Cog are free to
reproduce, so their items are in the app. HADS (Snaith & Zigmond / GL Assessment) and ISI (Morin)
are copyrighted, so ClerkMate records the score the learner obtained from the official form and
says why it is not reprinting the questions. MMSE and MoCA are excluded for the same reason —
MoCA additionally requires operator certification, which makes it the wrong instrument for a
student's phone. Every scale states its licence on screen.
- **Cardiovascular risk** — entirely learner-entered. ClerkMate neither computes the percentage,
  pre-fills the chart inputs, nor cross-checks them: knowing *which* variables a risk chart needs
  and transcribing them correctly is part of what is being learnt. The learner assembles age, sex,
  smoking status, systolic BP, diabetes and cholesterol unaided, reads the official chart, and
  records the result along with which chart they used. Those values print in the export, so a
  teacher can check the working rather than only the answer. Wiring an automatic lookup means
  adding the region's table to `config/cvd.ts`; inventing those numbers would be worse than not
  having them.

The Vietnamese wording of the PHQ and GAD items is a working translation for teaching, not a
formally validated Vietnamese version; replacing the `text` fields with a validated translation
needs no other change.

### One tap for "asked, nothing there"

An empty list is ambiguous — it may mean the question was never asked. Past medical history,
surgical history, allergies, family history and comorbidities each carry an explicit
"Không có" chip, so the learner closes the block in one tap and the completeness engine can tell
*chưa khai thác* apart from *đã hỏi, không có*. The exported record prints the difference too.

### Diagnosis for a multimorbid patient

Comorbidities are a first-class list, not a footnote: chẩn đoán chính → **chẩn đoán kèm theo** →
chẩn đoán phân biệt. Each comorbidity carries ICD-10/ICPC-2 and a control status (đang điều trị
ổn định / chưa đạt đích / mới phát hiện / chưa điều trị), and conditions already recorded under
past history can be pulled across in one tap. With more than one comorbidity the app prompts the
learner to state priority and interactions in the management plan.

### Examination: one tap for normal

Each system is `unchecked` / `normal` / `abnormal`. Choosing *normal* writes the standard
phrase from `EXAM_SYSTEMS[].normal` — a one-tap confirmation, still editable, and never applied
on the learner's behalf; `unchecked` is never treated as normal. "Tất cả bình thường" marks the
lot, then the learner describes only what was abnormal. The export separates abnormal findings
from normal ones.

### Learning reflection

`reflection` on the record holds what the learner took away: what they learned, where they
struggled, what they will do differently, questions for their teacher, a 1–5 self-rating and
free tags. The completeness engine only checks that it was **written** — it never scores the
content. It prints as its own section so the teacher reading the PDF sees the learner's
thinking, not just the chart.

### Completeness engine

`config/requirements.ts` holds one entry per documentable item:

```ts
{ id, label, sectionId, hint, isSatisfied(record), appliesTo?(record) }
```

`config/levels.ts` maps requirement ids to tiers per learner level, with `extends` for
inheritance — Y5 inherits Y2 and may promote an item from *recommended* to *mandatory*; the
stricter tier always wins. `appliesTo` lets an item drop out of scoring entirely (obstetric
history for a male patient is not counted as missing).

The percentage is weighted by tier (`TIER_WEIGHTS`: mandatory 3, recommended 2, optional 1)
and that table is editable in the same file.

**The engine never writes to the record and never invents clinical content.** It reports only
what has not been documented.

To change the teaching rules, edit `levels.ts`. To add a new documentable item, add one entry
to `requirements.ts` and reference its id from the levels. No component changes.

### Quick-note structuring

`heuristicStructurer` is rule-based and offline: diacritic-insensitive matching, clause
splitting, negation detection, and dictionaries for conditions, drugs, relations, occupations
and red flags.

**Abbreviations are understood**, which is how students actually write:

- conditions — `THA`, `ĐTĐ`, `RLLPM`, `BPTNMT`, `HPQ`, `TBMMN`, `NMCT`, `BTM`, `VKDT`, `THK`,
  `LX`, `VGB`, `GERD`, `XHTH`, `UTV`, `UTCTC`, `SXH`, `SGTT` and ~50 more
- vitals — `HA 140/85`, `M 78`, `NT 18`, `T 38.5`, `SpO2 96`, `CN 62kg`, `CC 155cm`, `VE 88`
- ages — `58 tuổi`, `62t`, `nam 45`
- drugs with doses — `amlodipine 5mg 1v/ngày`
- negation — `không hút thuốc`, `chưa ghi nhận dị ứng`

It handles mixed input such as:

> Nữ 58 tuổi, nội trợ. Đau khớp gối phải 3 tháng, tăng khi lên cầu thang. THA 10 năm, đang
> uống amlodipine 5mg 1v/ngày. Mẹ đái tháo đường. Không hút thuốc. HA 140/85, mạch 78.

Every proposal is a plain-data `StructuringSuggestion` carrying the snippet it came from, a
confidence level, and an `alreadyPresent` flag. The learner ticks what to accept; low-confidence
items and items already in the record start unticked. `applySuggestion()` in `parsing/apply.ts`
is the single applier registry.

**Adding an AI parsing layer later** means writing one more `NoteStructurer` that returns the
same suggestion shape. The appliers, the review UI and the acceptance flow are untouched. No
external API is used in this MVP.

### Genogram

`genogram/layout.ts` is a pure function from `FamilyMember[]` to coordinates — same input,
same output, no randomness and no image generation. Generation-based:

- `-1` parents · `0` patient, siblings, spouse · `+1` children

Symbols: square = male, circle = female, diamond = unspecified; teal fill = has a condition;
diagonal slash = deceased; double outline = index person. Couples join with a horizontal line,
descent drops to a sibship bar and then to each child. Sibship bars sit just above their own
row so they never cross the labels above, and a lone parent connects through a sideways elbow
for the same reason. Condition names are listed under the drawing rather than beside each
symbol, which keeps long Vietnamese diagnoses legible in print.

**Each condition gets its own hatch pattern** (`genogram/patterns.ts`) with a legend naming it:
diagonal, reverse diagonal, cross-hatch, horizontal, vertical, dots, checker, solid. Patterns
rather than colours carry the meaning, so the drawing survives a black-and-white print. A member
with several conditions is drawn as horizontal bands inside one symbol (up to four; the rest are
listed underneath). Assignment is deterministic — conditions are sorted with a Vietnamese
collator and take patterns in that order.

The patient's name, sex and age are **not** stored twice: `genogram/resolve.ts` reads the `self`
node's identity from `record.patient`, so a patient recorded as female can never be drawn as a
diamond, and the member editor shows those fields as read-only with a pointer to Hành chính. The
"Tên gọi trong phả hệ" field exists only to tell apart two people with the same relation ("Con
trai lớn" / "Con trai nhỏ") and falls back to the relation label when blank.

`genogram/lifeCycle.ts` suggests a life-cycle stage from the children's ages and the patient's
age, with the reasoning shown. Duvall's eight stages begin at marriage, so the list also carries
stage 0 (Carter & McGoldrick's single young adult) and stage 9 (living alone after divorce or
bereavement) — an unmarried or widowed patient is not forced into a stage that does not describe
them. It only ever *suggests*: the learner taps to accept, and the stage is the same field the
Family Medicine assessment edits.

Grandparents and more complex structures are a matter of extending the generation list and the
row builders; the renderer consumes whatever the layout emits.

### Export

The PDF is produced through the browser's own print pipeline: `export/CaseDocument.tsx` renders
the record, `styles/print.css` restyles it for A4, and `printRecord()` opens the print dialog
with a sensible filename. This keeps Vietnamese diacritics and selectable vector text without
bundling a font, and "Save as PDF" / Share is available on iOS Safari, Android Chrome and every
desktop browser. What the review screen shows is exactly what gets exported.

The exported record carries the learner's name, student ID and class in the header and footer,
and the filename is `ClerkMate_<studentId>_<case>_<date>` so a teacher can sort a folder of
submissions by student.

A one-line summary can also go out through `navigator.share` where supported. "Lưu bản sao dữ
liệu" writes a `.json` file — a machine-readable backup to reopen in ClerkMate, not something to
hand to a teacher.

## Level integrity

The learner's level is self-declared, and this is a local-first app with no accounts — a student
can set Y2 to be handed the full risk checklist. That cannot be *prevented* without a server and
an institutional login, so ClerkMate makes it **visible** instead, on the artefact the teacher
actually reads:

- every printed page carries a **watermark** with the level and student ID;
- a **stamp** under the header states the level the record was documented at and the scaffolding
  that level receives;
- the profile keeps a `levelHistory`, so a record exported after a downgrade prints
  *"Trình độ đã khai: SDH → Y2"* and flags that the change happened after the case began, or that
  the profile no longer matches the case;
- section 13 lists, per risk domain, **how much help the app actually gave** — the mode is stored
  on the recall entry when the learner commits, so it reports what happened rather than what the
  current level would give.

Combined with the learner's own pre-checklist list, which also prints, a teacher can see both the
declared level and the unaided thinking behind the record.

The profile itself is entered once. It persists in IndexedDB and the onboarding screen never
reappears; it is edited in Cài đặt.

## Demo cases

Two fictional cases ship with the app, picked to contrast rather than repeat:

| Case | Exercises |
|------|-----------|
| **Bà H., 58 — đau khớp gối** | SOCRATES and ICE, Family APGAR and SCREEM, three-generation genogram, cardiometabolic risk |
| **Ông T., 74 — té ngã tái diễn** | Seven active comorbidities with different control levels, polypharmacy, high falls risk, PHQ-2 positive escalating to PHQ-9, living alone after bereavement |

Both arrive with a mock lab slip attached, drawn on a canvas at seed time
(`demoCases/demoAttachments.ts`) rather than checked in as an image. The knee case's slip is left
**unredacted on purpose**, complete with an invented name and patient number across the top: the
redaction tool is impossible to try, or to demo to a judge, with an empty attachment list. The
elderly case's slip is already redacted, so the finished state is visible too. That also means the
knee case deliberately fails the `attachments.privacy` requirement until someone redacts it —
which is the completeness checker doing its job, not a gap in the demo data.

The second case is where the record earns its keep: it walks through why tightening HbA1c would
harm this patient, which is the kind of reasoning a completeness percentage can never capture —
and which is why the reflection section exists.

## Submission states and the hand-in flow

**Where the record actually goes.** The learner's flow ends at the PDF: preview, export, then send
the file to faculty over whatever channel the class already uses. Faculty install nothing, hold no
account, and are not expected to import anything — the product delivers its value without requiring
their adoption. Everything below describes the *optional* machinery around that: a lock that marks
which version was handed in, and a portable `.json` for backup, device-to-device transfer and
technical audit. It is kept because it works and is tested, not because the flow depends on it.

A record carries one of **eight processing states**: new · noting · in progress · complete ·
ready to submit · submitted · accepted · returned for revision.

**Five of the eight are derived**, recomputed from the record's own content on every read
(`workflow/status.ts`). A stored flag would drift away from the chart it describes; a pure
function cannot. Only the three person-caused states — submitted, accepted, returned — are
stored, each with its timestamp. A reviewer's decision stops governing the badge as soon as the
learner acts again (resubmits or reopens), so no record gets stuck at "returned" after it has
been fixed.

The hand-in flow (`workflow/submission.ts`) keeps the local-first architecture by **moving the
record rather than the user**: the state and the reviewer's comment travel inside the chart.

1. **Gate.** *Submit* only unlocks when no mandatory requirement is missing **and** every
   attachment has a sanitized derivative — with clinical photos additionally having answered the
   face question. Otherwise the button is disabled and names what is missing.
2. **Submit.** The app mints a submission code from the student id and date, stamps the time and
   **locks the record**. No file is pushed at the learner: the bundle (`.json`) is written only when
   they ask for it.
3. **The lock lives in the data layer.** `useCaseEditor.update()` refuses every edit on a locked
   record and explains why — rather than disabling inputs across 18 section editors, where one
   forgotten screen is a hole.
4. **Review.** The faculty member opens the bundle at `#/cham-bai` in the same app: learner
   identity, submission code, completeness, missing mandatory items, how many times the learner
   reopened the case, and the full read-only chart. They type a name and a comment, then choose
   *return for revision* (comment required) or *accept*. The app writes the decision into the
   record and downloads the result. **Nothing is stored on the reviewer's device.**
5. **Notify.** The learner opens the returned file from the home screen. Only the submission
   block is merged — their own clinical content stays authoritative. The comment then shows
   verbatim on every tab of that case, the list badges it *returned* + *new comment*, and the
   record unlocks.

Reopening is recorded (count and timestamps) and printed, so a resubmission is visible as one.
The PDF gains a section 21, *Faculty comments*, once a decision exists.

**What this is not.** There is no authentication: the reviewer types their own name, and the
printed record says so directly under the comment. A decision is not tamper-proof — anyone
holding the file can edit it. Notification means in-app, on file import: no email, no push. And
moving the file between the two people is manual. Real approval semantics would need a server,
accounts and signatures, which would end the local-first guarantee.

## Deliberately not in this MVP

Authentication · cloud sync · **a teacher dashboard across a cohort** · OCR · speech-to-text ·
AI diagnosis or treatment suggestions · appointment scheduling · billing · HL7/FHIR. These are
roadmap items.

There is no cohort-wide grading view, and no authenticated grading: a teacher opens one
submission bundle at a time and grades from the exported PDF, which carries the student's name
and ID. The learner's own assessment stays central — the completeness check (how complete is
this chart for my level?) plus the reflection (what did I learn?).

BMI uses the **WHO Asia-Pacific** cut-offs taught locally (<18.5 / <23 / <25 / <30), not the
international ones.
